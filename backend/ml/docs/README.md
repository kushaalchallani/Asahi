# Asahi ML Recommendation System Documentation

## Overview

The ML Recommendation System provides personalized mission recommendations for Asahi users based on their context, preferences, and historical interactions.

## Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│                    Mission Recommendation Pipeline                │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. User Check-in → Mood/Energy Detection                        │
│                            ↓                                    │
│  2. Safety Filters (hard constraints)                            │
│     - Low mood: prefer low-energy, non-social                  │
│     - Stressed: prefer regulation/environment                  │
│     - Lonely: prefer connection                                  │
│                            ↓                                    │
│  3. Rule-based Scoring                                           │
│     - Difficulty preference match                                │
│     - Feedback history                                           │
│     - Recent assignment penalty                                  │
│                            ↓                                    │
│  4. ML Model Scoring (when available)                            │
│     - Prediction probability for preference match                 │
│     - Historical user statistics                                 │
│                            ↓                                    │
│  5. Combined Ranking → Best Mission Recommended                  │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## Feature Engineering

### Mission Features (from database)

| Feature | Type | Description |
|---------|------|-------------|
| `category` | Categorical | regulation, connection, reflection, self-care, environment |
| `difficulty` | Categorical | low, medium, high |
| `energy_required` | Categorical | low, medium, high |
| `social_required` | Boolean | Whether mission requires social interaction |

### User Context Features

| Feature | Source | Description |
|---------|--------|-------------|
| `energy_preference` | Check-in text | Inferred from latest check-in feeling/note |
| `recently_seen` | UserMission history | Whether mission was assigned in last 7 days |

### Historical Features (derived from user history)

| Feature | Description |
|---------|-------------|
| `missions_completed_in_category` | Count of completed missions by category (capped at 10) |
| `missions_skipped_in_category` | Count of skipped missions by category |
| `missions_started_in_category` | Count of started missions by category |
| `missions_completed_similar` | Completes in same category as candidate |
| `missions_skipped_similar` | Skips in same category as candidate |
| `feedback_positive_ratio` | Ratio of "helpful" to total feedback |
| `time_since_last_low_energy_mission` | Days since last low-energy mission (capped at 30) |
| `preferred_category` | Most completed category |
| `preferred_difficulty` | User's set difficulty preference |

## Training Data Sources

### Primary: Real User Feedback

```python
# From export_feedback_dataset.py
records = export_feedback_dataset(db_session)
```

Training labels:
- `preference_match = 1`: User gave "helpful" feedback
- `preference_match = 0`: User gave "not_for_me" feedback

### Fallback: Synthetic Data

When insufficient real feedback is available (< 30 records with both classes), the system uses synthetic data generated by heuristics:

```python
preference_match = int(
    energy_required == energy_preference
    and difficulty == "low"
    and not recently_seen
    and not social_required
)
```

⚠️ **Important**: Results from synthetic-trained models are experimental and not proven to work in production.

## Label Generation Strategy

### Real Data Labels

1. Query `UserMission` records with explicit feedback
2. Match each feedback to the corresponding check-in
3. Infer energy preference from check-in text
4. Extract mission features
5. Compute historical features from user's prior interactions

### Handling Edge Cases

- **New users**: Use synthetic data until sufficient feedback accumulates
- **No check-in**: Default to "medium" energy preference
- **No historical data**: Default counts to 0

## Models

### Logistic Regression (Primary)

- **Purpose**: Main recommendation model
- **Settings**: `class_weight='balanced'`, `max_iter=1000`
- **Features**: All features with one-hot encoding

### Random Forest (Comparison)

- **Purpose**: Baseline comparison, feature importance analysis
- **Settings**: `n_estimators=200`, `class_weight='balanced'`
- **Features**: Same as Logistic Regression

### Dummy Classifier (Baseline)

- **Purpose**: Performance baseline
- **Strategy**: `most_frequent` (always predicts majority class)

## Evaluation Metrics

| Metric | Description |
|--------|-------------|
| Accuracy | Overall correctness |
| Balanced Accuracy | Accuracy accounting for class imbalance |
| Precision | Of positive predictions, how many were correct |
| Recall | Of actual positives, how many were predicted |
| F1 Score | Harmonic mean of precision and recall |
| ROC-AUC | Area under ROC curve |
| NDCG@5 | Ranking quality at top 5 recommendations |

## Inference Flow

1. **Load model**: `load_mission_model()`
2. **Build features**: `predict_mission_match(model, mission, energy_preference)`
3. **Predict probability**: `model.predict_proba(features)[0][1]`
4. **Rank candidates**: Sort by (difficulty_match, rule_score, ml_score)

## Fallback Strategy

If ML model is unavailable or fails:

1. Model fails to load → `load_mission_model()` returns `None`
2. Model prediction fails → Falls back to heuristic scoring
3. Rule-based ranking is used with `ml_score = 0.0`

This ensures recommendations continue to work even without ML.

## Safety Constraints

These constraints are **never overridden** by ML predictions:

1. **Low mood/loneliness**: Only recommend low-energy, non-social missions
2. **Stressed**: Only recommend regulation, environment, or reflection categories
3. **Negative feedback**: Penalize or exclude missions marked "not_for_me"

## Limitations

1. **Data scarcity**: New users get synthetic-trained models with experimental performance
2. **No temporal dynamics**: Model doesn't learn about time-of-day or seasonality
3. **No deep personalization**: Same model for all users (no user embeddings)
4. **Label quality**: "helpful"/"not_for_me" feedback may be noisy
5. **Feature leakage**: Historical features use info available at recommendation time only

## Improvement Pathways

As real user interaction data accumulates:

1. **More real feedback**: Switch from synthetic to real training data
2. **Longer history**: Track completion rates over time
3. **Engagement signals**: Use time-to-complete as implicit satisfaction
4. **Category preferences**: Learn user's category affinities
5. **Adaptive thresholds**: Tune prediction thresholds per-user
